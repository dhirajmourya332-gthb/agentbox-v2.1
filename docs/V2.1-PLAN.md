# agentbox v2.1: diff review and visual plan approval

v2.1 is built on top of v2 in a sibling folder (`grok-alt-v2.1`, cloned from `grok-alt-v2` main). It adds two features, chosen from `docs/COMPETITOR-GAPS.md`:

1. **Diff review:** see what a task changed, comment on lines, and approve, request changes, or reject.
2. **Plan approval, led by a diagram:** before coding, the agent submits a short plan whose first and largest element is a simple before/after diagram.

---

## 1. Plan approval

### Why a diagram first
Agent plans tend to be long walls of text. One picture of "what exists → what will exist" answers most of what the owner needs to decide: what's new, what goes away, and what's rewired. The text only supports the picture.

### What the agent submits (`mcp__team__submit_plan`)

| Field | Limit | Shown |
|---|---|---|
| `title` | 80 chars | header |
| `summary` | 1–2 sentences, 280 chars | under the title |
| `diagram.before` / `diagram.after` | graphs; **after ≤ 10 boxes, ≤ 14 arrows**; labels ≤ 32 chars | **top, large** |
| `changes` | ≤ 6 bullets, 140 chars each | under the diagram |
| `checks` | ≤ 5: how we'll know it works | under changes |
| `risks` | ≤ 3 | under checks |
| `details` | optional markdown, 8000 chars | collapsed ("Full plan") |

A graph is `{ nodes: [{ id, label, change? }], edges: [{ from, to, label? }] }`. The same `id` in `before` and `after` means the same component. `change` is a short note (≤ 60 chars) for a component that stays but behaves differently.

**Example** (the owner's own example):
```
before: service1 → service2
after:  service1 → logger-service (new)
        service1 → service2
```

The server rejects plans that break the limits, with an error that tells the agent how to simplify ("show only the parts that change and their direct neighbours"). It enforces simplicity rather than hoping for it.

### How it's drawn
One merged diagram shows the change at a glance:
- **New** boxes and arrows are green, marked "new".
- **Removed** ones are red, dashed, marked "removed".
- **Changed** boxes are amber, with the note under the label.
- **Unchanged** ones are grey.

Tabs switch between **Change** (the default), **Before** and **After**. The layout runs left to right and is computed with dagre; the SVG is drawn by agentbox, with no diagram language for the agent to get wrong.

### Flow
1. **Gate:** on New task, **"Approve a plan first"** switches the gate on for that piece of work. Agents can also submit a plan on their own for big or risky changes.
2. **Submit:** the agent calls `submit_plan` and ends its turn. The plan appears as a card in the conversation and as a needs-you item.
3. **Decide:** the owner chooses **Approve** (with an optional note), **Request changes** (with feedback; the agent revises and resubmits, and the new version replaces the old) or **Reject** (the agent stops and reports).
4. **Callback:** the deciding message is sent to the agent, which starts its next turn.
5. **Enforcement:** while the gate is on and no plan is approved, `Edit`, `Write` and `NotebookEdit` inside the task's repo worktrees are refused with "this work needs an approved plan first". The instruction layer says so too.

## 2. Diff review

### What it shows
A **Changes** tab on the task covers each repo worktree of the work:
- branch, base, commits ahead;
- the file list with +/- counts;
- a unified diff per file, including uncommitted and new files.

Large files and diffs are cut off with a note. Binary files are listed but not shown.

### Reviewing
- Click a line to add a comment.
- The review bar holds an overall note plus **Approve**, **Request changes** and **Reject**.
- The review goes to the agent as one message, with every comment as `repo/path:line — text`, and starts its turn:
  - **Approve:** "carry on: open/update the PR, or merge if your rules allow".
  - **Request changes:** "address every comment, then report".
  - **Reject:** "stop; don't push or merge this".
- Reviews are stored, and the tab shows the latest review's state.

## 3. Out of scope for v2.1
- Comments posted back to GitHub PRs (the review stays in agentbox).
- Plan and review cards in the Android app (they show as needs-you items only).
- Diagrams elsewhere (repo maps, architecture docs). The renderer is reusable for that later.
