# agentbox v2.1: diff review and visual plan approval

v2.1 is built on top of v2 in a sibling folder (`grok-alt-v2.1`, cloned from `grok-alt-v2` main). It adds three features, the first two chosen from `docs/COMPETITOR-GAPS.md`:

1. **Diff review:** see what a task changed, comment on lines, and approve, request changes, or reject.
2. **Plans led by a diagram:** a short plan whose first and largest element is a simple before/after diagram. It waits for the owner only when asked to.
3. **Roadmaps:** live progress maps for big work, readable at a glance.

---

## 1. Plan approval

### Why a diagram first
Agent plans tend to be long walls of text. One picture of "what exists → what will exist" answers most of what the owner needs to decide: what's new, what goes away, and what's rewired. The text only supports the picture.

### What the agent submits (`mcp__team__submit_plan`)

| Field | Limit | Shown |
|---|---|---|
| `title` | 80 chars | header |
| `summary` | 1–2 sentences, 280 chars | under the title |
| `diagram.before` / `diagram.after` | graphs; **after ≤ 10 boxes, ≤ 14 arrows**; labels ≤ 32 chars | **top, large** |
| `changes` | ≤ 6 bullets, 140 chars each | under the diagram |
| `checks` | ≤ 5: how we'll know it works | under changes |
| `risks` | ≤ 3 | under checks |
| `details` | optional markdown, 8000 chars | collapsed ("Full plan") |

A graph is `{ nodes: [{ id, label, change? }], edges: [{ from, to, label? }] }`. The same `id` in `before` and `after` means the same component. `change` is a short note (≤ 60 chars) for a component that stays but behaves differently.

**Example** (the owner's own example):
```
before: service1 → service2
after:  service1 → logger-service (new)
        service1 → service2
```

The server rejects plans that break the limits, with an error that tells the agent how to simplify ("show only the parts that change and their direct neighbours"). It enforces simplicity rather than hoping for it.

### How it's drawn
One merged diagram shows the change at a glance:
- **New** boxes and arrows are green, marked "new".
- **Removed** ones are red, dashed, marked "removed".
- **Changed** boxes are amber, with the note under the label.
- **Unchanged** ones are grey.

Tabs switch between **Change** (the default), **Before** and **After**. The layout runs left to right and is computed with dagre; the SVG is drawn by agentbox, with no diagram language for the agent to get wrong.

### When agents plan (nothing waits by default)
Agents handle low- and medium-risk work themselves, end to end, with no plans and no approvals. Planning never becomes a step the owner has to answer, unless the owner asks for it.

| Situation | What the agent does | Owner |
|---|---|---|
| **Default** | Just does the work. For a high-impact design change (a new service, a changed data flow or schema) it *may* share a plan, then carries on in the same turn. | Nothing to answer, and no "needs you" item. The card offers **Looks good / Redirect… / Stop…** in case they look and want another direction. |
| **"Approve a plan first"** (ticked on New task or in the task panel) | Explores, submits a plan, and waits. Until a plan is approved, edits inside repo worktrees and git commits/pushes are refused. | A "needs you" item, with **Approve / Approve with a note / Request changes / Reject**. |
| **The owner asks for a plan in words** | Submits with `wait_for_owner: true` and waits. | Same as above (no edit lock). |

Decisions call the agent back. "Request changes" on a waiting plan means revise and resubmit. "Redirect" on a shared plan means adjust the work already under way. A newer plan replaces an older open one.

## 2. Diff review

### What it shows
A **Changes** tab on the task covers each repo worktree of the work:
- branch, base, commits ahead;
- the file list with +/- counts;
- a unified diff per file, including uncommitted and new files.

Large files and diffs are cut off with a note. Binary files are listed but not shown.

### Reviewing
- Click a line to add a comment.
- The review bar holds an overall note plus **Approve**, **Request changes** and **Reject**.
- The review goes to the agent as one message, with every comment as `repo/path:line — text`, and starts its turn:
  - **Approve:** "carry on: open/update the PR, or merge if your rules allow".
  - **Request changes:** "address every comment, then report".
  - **Reject:** "stop; don't push or merge this".
- Reviews are stored, and the tab shows the latest review's state.

## 3. Roadmaps

### Why
For big work, the chat says what happened but not where things stand. A roadmap is a small labelled set of steps that the agents keep current, so the owner sees what's done, in progress, blocked and next without reading.

### What agents do
- **`roadmap_create`:** a label (e.g. "Partner API keys") and up to 40 steps. Each step has an id, a title, and optionally a phase, `after` (dependencies), status, owner, note and link.
  - The server refuses a step that depends on a missing step, and dependencies that form a circle.
  - A piece of work can have several roadmaps, one per stream, each with its own label.
- **`roadmap_update`:** only what changed. That covers:
  - status: to do → doing → done, blocked (with the reason in the note), or skipped;
  - the owner and a link (PR, issue or doc);
  - adding, removing, renaming or re-linking steps.

  Any agent working on that piece of work may update it, including helpers it delegated to.
- **Keeping it current:** every turn, the work's instructions list each roadmap compactly, with its id and every step's state. Agents are told to update it as soon as something happens.
- **When:** for big work only (several steps, phases or agents). Small tasks don't get one.
- **Automatic state:** a roadmap is *done* when every step is done or skipped, and *active* again when one isn't. The last 20 changes are kept, with who made them and when.

### What the owner sees
- **Progress strip** under the task (or task room) header, one slim line per roadmap:
  - a progress ring, the label and a count;
  - a row of status dots;
  - what's in progress or blocked right now.

  One click opens the map.
- **Card** in the conversation where it was created. It shows the latest state, updated in place and never re-posted:
  - the **metro line** (one dot per step in order, grouped by phase: done ●, in progress ◉ pulsing, blocked ● red, to do ○, skipped –);
  - **Now / Blocked / Next** ("Next" means ready to start: all its dependencies are done);
  - the latest change.
- **Roadmaps tab** in the task panel: every roadmap of the work.
- **Full screen**, with a switch between the work's roadmaps:
  - **Map:** steps and their dependencies, coloured by status, with met dependencies solid and pending ones dashed. Clicking a step opens its link.
  - **List:** by phase, with owner, note, time and link, plus the recent changes.
- **Archiving** (`POST /api/roadmaps/:id/archive`, owner only) removes a roadmap from the agents' view and the strip.

## 4. Who does what, enforced

All agents run as the same Linux user, so every connected integration's credentials (`~/.aws`, `~/.kube`, `gh`…) are reachable by all of them. In v2, mapping an integration to a role only decided whose instructions mentioned it. v2.1 enforces the mapping, plus the orchestrator role.

### Integration CLIs follow the mapping (`integrationGuard`)
- Each integration's `module.yaml` lists the CLIs that belong to it:

  | Integration | CLIs |
  |---|---|
  | aws | `aws`, `session-manager-plugin` |
  | kubernetes | `kubectl`, `helm`, `k9s`, `kustomize` |
  | gcp | `gcloud`, `gsutil`, `bq` |
  | azure | `az` |
  | gitlab | `glab` |
  | github | `gh` |
- A shell command that *runs* one of them (directly, through `sudo`/`env`/`timeout`/`xargs`, by path, in a pipe, or inside `bash -c '…'`) is refused for a role that isn't mapped to that integration. Only mentioning one is fine, e.g. `grep kubectl docs/`.
- The refusal names the teammates who have it and tells the agent to delegate. If nobody has it, the agent is told to raise a setup request.
- Claude's built-in subagents go through the same hooks. The setup agent is exempt.

### Orchestrators don't do hands-on work (`orchestratorGuard`)
A role with **Plans and delegates** (e.g. tech-lead) can't do the following:
- edit files inside repo worktrees or clones;
- `git commit`, `merge`, `rebase`, `cherry-pick`, `revert`, `apply`, `am`, `stash pop` or `reset --hard`;
- write into a repo from the shell.

Reading code, running checks to review, its own notes and docs, the work's shared folder, and `gh` issues, PRs, reviews and merges stay allowed. Its instructions say: find the simplest, most elegant solution, delegate every piece to the right teammate, review, merge and report.

### Everyone: stay in your lane
- The platform layer tells every agent to use only its own tools and integrations, and to delegate the rest.
- Claude's built-in subagents are for reading and searching within the agent's own job.
- The team roster lists each teammate's tools, e.g. "Tools: AWS, GitHub, Kubernetes".

These are guardrails for well-meaning agents, not a sandbox. Separate unix users per role (H3) would make them hard limits.

## 5. Out of scope for v2.1
- Comments posted back to GitHub PRs (the review stays in agentbox).
- Plan and review cards in the Android app (they show as needs-you items only).
- Diagrams elsewhere (repo maps, architecture docs). The renderer is reusable for that later.
